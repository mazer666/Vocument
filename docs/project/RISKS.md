# Vocument Risk Register

Tracked according to `PROJECT_MANAGEMENT.md` §9.

| ID | Description | Probability | Impact | Mitigation | Owner Role | Status |
|---|---|---|---|---|---|---|
| `RISK-001` | Concurrent access to mutable MuPDF state across threads causes crashes or memory corruption | Medium | Critical (S4) | Enforce serialized `DocumentActor` per session; only immutable display-lists/tiles run on worker threads (`ARCHITECTURE.md` §7) | ROLE-04 (PDF/MuPDF) | Active |
| `RISK-002` | External file modification (Finder, iCloud, SAF provider) races with local save and causes silent data loss | Medium | Critical (S4) | Multi-signal file identity check before atomic replacement; mandatory conflict UI (`ARCHITECTURE.md` §14, §16) | ROLE-03 (Rust Core) | Active |
| `RISK-003` | Visual-only redaction leaves underlying text, OCR layer, or hidden objects extractable | Low | Critical (S4) | Two-stage redaction with mandatory independent reopen/search/extract verification (`ARCHITECTURE.md` §29) | ROLE-09 (Security) | Active |
| `RISK-004` | UniFFI boundary leaks engine internals or blocks future out-of-process worker isolation | Low | High (S3) | Restrict UniFFI surface to opaque handles, immutable DTOs, and `EngineTransport` abstraction (`ARCHITECTURE.md` §5, §37) | ROLE-02 (Architect) | Active |
| `RISK-005` | Large scan PDFs exhaust mobile RAM on Android | Medium | High (S3) | Adaptive tile cache with strict memory budgets (`config/performance-budgets.toml`) and OS memory-pressure eviction | ROLE-14 (Performance) | Active |
| `RISK-006` | The Android build must link a real MuPDF engine. The placeholder bridge was removed; MuPDF 1.28.5 is now cross-compiled for `aarch64-linux-android` with the NDK (`scripts/prepare-android-mupdf.sh`) | Low (residual) | Critical (S4) | The placeholder bridge is deleted from the tree, `scripts/validate-repo.sh` rejects any placeholder PDF engine, and `scripts/build-android-rust.sh` verifies that the produced library depends on `libmupdf` and not on a stub | ROLE-04 (PDF/MuPDF) | Mitigated |
| `RISK-007` | The job execution layer has a bounded worker pool, but job pause/resume, job dependencies and resumability across process restarts are not implemented; a task graph would be required (`ARCHITECTURE.md` §8.1) | Medium | High (S3) | Scope recorded in `ARCHITECTURE.md` §8.1 and `ROADMAP.md` M1.5; the current model satisfies `JOB-004` … `JOB-009` and is used by both platforms | ROLE-03 (Rust Core) | Active |
| `RISK-008` | Platform-specific differences could leak into the shared core as target-specific branches, which would make the planned Windows and Linux tracks expensive and risky | Medium | High (S3) | `PLATFORM-003` … `PLATFORM-005` in `REQUIREMENTS.md` and `CR-0003` require platform traits in the core and a platform-neutral FFI surface; the platform order is binding | ROLE-02 (Chief Architect) | Active |
| `RISK-009` | The AGPL requires the Android distribution to offer the corresponding source of the linked MuPDF. The mechanism (in-app link, source archive in the APK, or a build-time source bundle) is not yet decided | High | High (S3) | Recorded in `ADR-0017`; the MuPDF source revision is already pinned by the build script, so the source can be provided from the same revision. Must be settled before the first public Android release | ROLE-18 (Licensing) | Open |
| `RISK-010` | Linking the real MuPDF engine grows the Android package. Measured in M1.6: `libmupdf.so` is 56 MB, `libvocument_ffi.so` is 101 MB in the debug build but only 11 MB after the debug information is removed, and the debug package reaches 250 MB against 23 MB for the stripped release build | High | Medium (S2) | The release profile strips the debug information (`scripts/build-android-rust.sh`), which removes about 90 MB. Further reduction is possible by enabling MuPDF build options that drop the unused formats (XPS, CBZ, HTML/EPUB) and by shipping per-ABI splits. The package size is measured as part of the release check | ROLE-16 (Supply Chain) | Open |
| `RISK-011` | The native libraries that are shipped inside the Android package cannot be resolved by the Android dynamic linker. A `DT_NEEDED` entry is resolved by the **exact** file name, and the packaging step only includes files ending in `.so`. A versioned SONAME such as `libmupdf.so.28.5` therefore never reaches the package, and the process fails to start | Low (residual) | Critical (S4) | Found and fixed in M1.6: MuPDF is linked for Android with an unversioned SONAME (`-Wl,-soname,libmupdf.so`). `scripts/verify-android-native-libs.sh` checks the resolvable dependency closure, the SONAME agreement, the architecture and the 16 KB page alignment of every shipped library. A release without a green gate must not be published | ROLE-16 (Supply Chain) | Mitigated |
| `RISK-012` | The native libraries are built for 4 KB memory pages. Android 15 and later devices may use 16 KB pages, where every `PT_LOAD` segment must be aligned to at least `0x4000`. A library with a smaller alignment does not start on such a device | Low (residual) | Critical (S4) | Fixed in M1.6: all links request `-Wl,-z,max-page-size=16384`; `scripts/verify-android-native-libs.sh` rejects a library with a smaller alignment | ROLE-16 (Supply Chain) | Mitigated |
| `RISK-013` | The application interface blocks while native work runs. The scan pipeline is offloaded, but the viewport rendering, the page prefetch and the page thumbnails were called synchronously from the UI thread | Low (residual) | High (S3) | Fixed in M1.6: the viewport render runs on a background executor and publishes its result to the Compose state; the thumbnails are produced with `produceState`. The runtime measurement on a device is still **NOT RUN** | ROLE-12 (Android) | Mitigated |
| `RISK-014` | A job body that ignores its cancellation token blocked the shutdown of the worker pool indefinitely. Because the executor stops the pool in its `Drop`, such a job could also prevent the **application from exiting** | Low (residual) | High (S3) | Fixed in M1.6 in two steps: `shutdown()` signals the cancellation token of every running job before it joins the workers, and the wait for the workers is bounded by `shutdown_grace_ms` (default 2 s); a worker that is still stuck is detached instead of blocking the shutdown forever. The tests release their blocker through a guard in every exit path, so a failing test reports the defect instead of hanging the run | ROLE-03 (Rust Core) | Mitigated |
| `RISK-015` | The build environment is memory constrained. The release build runs the dexer and the lint analysis together; with a 2 GB Gradle heap the daemon was killed during the packaging step and left a **truncated APK** behind, which can be mistaken for a valid build artefact | Medium | High (S3) | The Gradle heap is limited to 1 GB in `apps/android/gradle.properties`, and the build is verified by the exit code and by the inspection of the produced package. A truncated archive must be rejected, never published | ROLE-16 (Supply Chain) | Mitigated |
| `RISK-016` | A document of a platform document provider (an Android `content://` URI) has no local path. The local file broker would turn the URI into a nonsense file name and write a file with that name in the working directory — a stray file with the name of the URI, and the document itself would not be saved at all | Medium | High (S3) | The capability to write a file back now belongs to the broker (`FileBroker::can_write_back`). A document provider URI is refused with a typed error (`NotLocallyWritable`), and `ScopedLocalFileBroker::stage_write` rejects URI tokens as a last line of defence. The platform shell writes the document into a place the user owns, through the export (`export_session_bytes`) | ROLE-03 (Rust Core) | Mitigated |
| `RISK-017` | The files that the application writes for a document of the user — the staging file of a save, the recovery container with its manifest and journal — are readable for anyone else on the machine, if the system default applies | Low (residual) | High (S3) | The staging file is created with `0600`, the recovery container with `0700`, the manifest and the journal with `0600`. The mode is asserted by a test | ROLE-09 (Security) | Mitigated |
| `RISK-018` | The camera stays bound after the view has left the interface. The privacy indicator of the system stays on, and the camera continues to draw power | Low (residual) | Medium (S2) | The camera is unbound in `onDispose`. The state of the interface is published on the main thread only, the analysis itself stays on the camera thread. The runtime behaviour on a device is still **NOT RUN** | ROLE-12 (Android) | Mitigated |
| `RISK-019` | A redaction removes the text from the page, but the removed text stays in the file: the old content stream is written as an unreferenced object. The document looks redacted and still contains the secret | Medium | Critical (S4) | Found while implementing M2.1: MuPDF writes unreferenced objects unless the garbage collection is requested. The write options now set `do_garbage = 1`. The verification in the core checks four things — the extraction, the search, the rendered page and the bytes of the file — and the gate `scripts/validate-repo.sh` insists on the test | ROLE-09 (Security) | Mitigated |
| `RISK-021` | The redaction removes the text layer, but the picture of the page still carries the words. A scan stores its text twice: as an invisible text layer and as pixels in the image. A redaction that only removes the text layer leaves the image readable | Medium | Critical (S4) | Found while hardening M2.1: the image option of the engine was wrong. The redaction now replaces the pixels of the image under the region (`PDF_REDACT_IMAGE_PIXELS`) and leaves the rest of the image intact. The proof is a marker inside the uncompressed image stream, which is gone from the file after the redaction | ROLE-09 (Security) | Mitigated |
| `RISK-022` | The redaction covers the removed region with a drawn black box. The covering hides content that survived the removal, and the verification reads the covering instead of the content | Medium | Critical (S4) | Found while hardening M2.1: the box is switched off (`black_boxes = 0`). The picture of the page shows the truth, and the verification renders the page and reads it with the OCR. The removed region is empty in the rendering, and a test asserts it | ROLE-09 (Security) | Mitigated |
| `RISK-023` | A redaction that removes nothing, or whose removal cannot be verified, is reported as a success. The user believes the document is clean | Low (residual) | High (S3) | A region without text and without visible content is refused (`NothingToRemove`). A verification that did not pass in every aspect is reported over the FFI boundary as the error `RedactionUnverified` — there is no way to treat an unverified redaction as a success. A redaction that cannot be verified is additionally **rolled back**: the document keeps the bytes it had before the attempt, so the user does not hold a changed document | ROLE-09 (Security) | Mitigated |
| `RISK-024` | The removed text survives in a place of the document that does not lie on the page — the text of an annotation, the value of a form field, the metadata, the XMP packet, an embedded file. The redaction reports a success while the secret is still in the document | Medium | Critical (S4) | Found by the independent adversarial audit of M2.1: MuPDF removes the content of the page and nothing else, and the check over the bytes only saw plain text — a text stored as UTF-16 or as the hex string of the UTF-16 bytes was not found. The engine now cleans the annotations, the form values and the metadata and reports every place of the document that still carries the word, in all of these encodings. A place that cannot be cleaned (an embedded file) makes the redaction fail | ROLE-09 (Security) | Mitigated |
| `RISK-025` | The redaction removes only a part of a word and leaves a fragment behind. The verification compares whole words, so the fragment is reported as a success | Medium | Critical (S4) | Found by the independent adversarial audit of M2.1: the removal works character by character. The verification now compares fragments — a word that is a prefix or a suffix of a removed word is a survivor — and it checks the redacted region itself: nothing may lie in it any more | ROLE-09 (Security) | Mitigated |
| `RISK-026` | The word boxes of a turned page (`/Rotate`) are inverted, so the redaction misses the text on a very common page orientation | Medium | High (S3) | Found by the independent adversarial audit of M2.1: the box of a word was built from the upper-left and the lower-right corner of a character, which is not the order of the corners on a turned page. The box is now the bounding box of all four corners of all of its characters, and the distance between two characters is measured along the reading direction of the line | ROLE-09 (Security) | Mitigated |
| `RISK-027` | The text of a Type 3 font is not removed by MuPDF (`recurse = 0`). A document that uses one is reported as redacted while the text is still on the page | Low (residual) | High (S3) | The first independent audit of M2.1 measured 8322 dark pixels before and after the redaction. **The second audit could not reproduce the premise**: MuPDF 1.28.5 removed the text of a Type 3 font completely in the construction it built (glyph procedures, char procs, `/Differences`). The claim is therefore withdrawn for that construction; the other constructions — glyph procedures with their own CTM, a Type 3 font in an XObject — were not checked exhaustively. Should such a construction survive, the check over the region sees the text that survived and the redaction is refused | ROLE-09 (Security) | Mitigated (residual) |
| `RISK-028` | A word that is only partly covered leaves a readable fragment behind ("GEHEIM" → "HEIM"), and the report does not mention it: the word was not in the list of the removed words, because its centre lay outside the marked region | Medium | Critical (S4) | Found by the second independent audit of M2.1. The rule is now: a word that the region **touches** belongs to the redaction, and the region grows to the box of the whole word, so the word goes as a whole. The words of the picture count as well. Proof: `a_region_that_only_covers_a_part_of_a_word_removes_the_whole_word`, `a_region_grows_to_the_words_it_touches` | ROLE-09 (Security) | Mitigated |
| `RISK-029` | An error **after** the removal leaves the document changed and reports an error that says nothing about the state: the user holds a changed document and believes it is the old one | Medium | Critical (S4) | Found by the second independent audit of M2.1. Every error after the removal — the text extraction, the reindexing, the rendering of the page, the reading of the bytes — puts the document back now. A rollback that fails itself is reported as its own error (`RedactionRollbackFailed`), and the user is told to open the document again | ROLE-09 (Security) | Mitigated |
| `RISK-030` | The crash recovery applies a redaction **without verification** to the document from the disk: the journal cannot say whether the redaction was ever verified, and the process may have died between the removal and the verification | Low | High (S3) | Found by the second independent audit of M2.1. The recovery does not replay a redaction any more: the document is restored to the state before it, and the message of the recovery says so. Proof: `the_recovery_does_not_replay_a_redaction` | ROLE-09 (Security) | Mitigated |
| `RISK-031` | The checkpoints of the recovery store hold the document in plain text and were readable for everybody on the machine (`0644`) | Low | High (S3) | Found by the second independent audit of M2.1. The checkpoints belong to the user alone: the directory is `0700`, the file `0600` | ROLE-09 (Security) | Mitigated |
| `RISK-032` | The redaction is not reachable for the user: no application calls it, so the chain ends in the generated code and the report is never shown | Medium | High (S3) | Found by the second independent audit of M2.1. The macOS client and the Android bridge call the redaction and check the report themselves — the `verified` flag is not trusted, the four checks are looked at. The step of the interface (the user marks the region and sees the report) belongs to the macOS slice of M2 and is **NOT RUN** here | ROLE-09 (Security) | Open |
| `RISK-033` | The redaction works with a **list of known places** of the document. A secret that stands in a place the list does not know — the popup of an annotation that does not stand in `/Annots`, the structure tree, the name tree, the optional content, the private data of a page — survives, and the redaction reports a success | High | Critical (S4) | Found by the third independent audit of M2.1. The search for the places and the cleaning now walk through **every** object of the document (`mupdf_walk.h`) — pages, annotations with their popups, form fields, metadata, the structure and name tree, the optional content, the private data and the embedded files. Every string and every stream is offered with the place it lies in. Proof: `the_places_that_a_list_of_known_places_does_not_reach_are_found`, `the_places_that_a_list_of_known_places_does_not_reach_are_emptied` | ROLE-09 (Security) | Mitigated |
| `RISK-034` | The redaction reports a success while the same text still stands somewhere else in the document, and the user is not told. The user believes the secret is gone | Medium | High (S3) | Found by the third independent audit of M2.1. The report names the places where the same text still stands (`remaining_occurrences`) and the places that could not be read (`uninspected_places`); the macOS client and the Android bridge turn them into warnings that the shell has to show. The step of the interface is still missing (RISK-032) | ROLE-09 (Security) | Mitigated (the surface is open) |
| `RISK-035` | A place of the document that could not be read — the content of an attached archive — is treated as if it were clean. The secret stays in the archive | Low (residual) | High (S3) | Found by the third independent audit of M2.1. The redaction names such a place and does not claim that the text is gone from there. An attachment is never deleted: the data of the user belongs to the user | ROLE-09 (Security) | Mitigated (residual) |
| `RISK-036` | The rendered tiles of the page with the removed text stay in the cache of the process. The text is readable in the memory of the process until the cache evicts it | Low | Medium (S2) | Found by the third independent audit of M2.1. The tiles and the thumbnails of the document are dropped after a redaction | ROLE-09 (Security) | Mitigated |
| `RISK-037` | The clipboard of the user keeps the removed text, and the clipboard history of the system keeps it as well | Low | Medium (S2) | Found by the third independent audit of M2.1. The clearing belongs to the redaction surface; no application calls the redaction yet, so there is no place where it could happen. The macOS app and the Android app are named as the place of the change | ROLE-09 (Security) | Open |
| `RISK-020` | A redaction is undone, or restored from the recovery store, and the removed content is readable again | Low (residual) | Critical (S4) | A redaction has no inverse: the undo is refused explicitly. The checkpoints of the recovery store, which hold the bytes of earlier states, are deleted with the redaction, and the transaction command carries no text, so the persistent journal does not contain the removed content either | ROLE-09 (Security) | Mitigated |
