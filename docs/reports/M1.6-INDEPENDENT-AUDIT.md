## 3. Refuted, incomplete or unproven claims

### W1 — "Android does not block the UI thread" (refuted, part of the way)

**Claim in `M1.5-ACCEPTANCE.md`, line "Android offloading":**
> "the capture pipeline (edge detection, perspective correction, cleanup, OCR) runs on a background executor; only the status strings are published to the Compose state."

**Finding:** that is true **for the scan path**, but it did not hold for the
other native calls of the interface. Two call contexts ran **on the UI
thread**:

1. `MainActivity.kt` → `refreshViewport()` → `coreBridge.renderViewportWithPrefetch(...)`.
   The call happened in Compose event handlers (`onSelectPage`, `onPageChange`,
   `onScaleChange`, `onMemoryPressure`, `onDocumentSessionOpened`). The function
   renders **the viewport and prefetches the neighbouring pages** — so several
   MuPDF renderings — synchronously on the UI thread.
2. `NavigationAndSearchPanel.kt` → `remember(sessionId, pageIndex) { renderPageThumbnail(...) }`.
   A `remember` block is evaluated **during the composition**. Every thumbnail
   of the navigation list was therefore rendered synchronously on the UI
   thread.

The camera frame path was correct (`setAnalyzer(cameraExecutor)` with its own
executor) and `ScanCaptureScreen` already used the background executor.

**Assessment:** the statement was not false, but **incomplete**, and in the
acceptance record it was read as a blanket freedom of the UI. It is now
corrected (section 5, change A4).

### W2 — "The Android libraries are integrated correctly" (refuted, severe)

**Claim:** the native integration is correct, and the verified resolution of
the SONAME is "proof".

**Finding:** the production of the Android APK revealed two independent
defects which together meant that **`libmupdf.so` never landed in the APK**:

| # | Defect | Evidence |
|---|---|---|
| a | `libvocument_ffi.so` demanded `libmupdf.so.28.5` (the SONAME of MuPDF), but the `jniLibs` directory contained `libmupdf.so`. The Android loader resolves `DT_NEEDED` by **exact file name** — the process would have failed at the start with `cannot open shared object file`. | `readelf -d` showed `NEEDED: libmupdf.so.28.5`, the directory contained `libmupdf.so` |
| b | Even with the correct name the file would **not** have landed in the APK: Gradle's JNI packaging only captures `*.so`, and `libmupdf.so.28.5` does not end in `.so`. | `unzip -l app-debug.apk \| grep -c libmupdf` → **0** |

**Assessment:** the previous proof (`readelf` showed the correct `DT_NEEDED`
entry) was correct, but it did **not** check the actual resolvability in the
package. That is exactly the gap the task named.

### W3 — 16 KB memory page compatibility (not checked, not fulfilled)

**Finding:** all four delivered libraries had `p_align = 0x1000` (4 KB).
Android 15 and later can use 16 KB pages; there every `PT_LOAD` segment must
be aligned to at least `0x4000`. The NDK linker demands that explicitly.

**Evidence:** `readelf -lW` over all libraries → uniformly `0x1000`.

### W4 — `shutdown()` asks running work to stop (documentation vs. implementation)

**Claim in the doc comment of `JobExecutor::shutdown`:**
> "Stops the pool: queued work is dropped, running work is asked to stop."

**Finding:** the implementation only discarded the queue. The cancellation
tokens of running jobs were **never** signalled. A running job only noticed
the termination when it finished on its own; `handle.join()` then blocked
without a limit. With a hanging engine call the shutdown blocked
permanently.

**Additional finding:** a test failure thereby became a **hang** instead of an
error message — the panic path led via `Drop` into `shutdown()` and then into
the `join()` of a blocked worker.

### W5 — APK size (not investigated)

**Claim in `RISK-010`:** "roughly 55 MB".

**Finding:** the native library `libvocument_ffi.so` was **101 MB** in the
debug build, of which **~92 MB DWARF debug information**. The actual code is
~9 MB. The 55 MB referred only to `libmupdf.so`.

## 4. Conclusiveness of the tests — mutation samples

The central question: **would the test also be green if the implementation
were broken?** Two fault injections were made and rolled back.

### M1 — `running_count` no longer counts up

```text
Mutation:  running_jobs.fetch_add(1, Ordering::AcqRel);  →  removed
Result:    test `running_count_reflects_the_jobs_that_execute` failed
```

The test detects the mutation. **It, however, caused a hang instead of an
error message**, because the blocker of the test worker was not released when
the assertion failed. That is a defect of the test hygiene, not of the
production — a hanging test is worse than a failing one, because it consumes
the entire CI timeout without naming the defect.

**Fixed:** a `BlockerGuard` releases the blocker when the test is left,
independently of the test result. The test now reports a clear `FAILED` with
an error message in 5.24 s.

### M2 — `shutdown()` no longer signals the running jobs

```text
Mutation:  let _ = self.tracker.cancel_all_running();  →  removed
Result:    test `shutting_the_pool_down_asks_the_running_jobs_to_stop` FAILED
           panicked at executor_tests.rs:480
           test result: FAILED. 11 passed; 1 failed; finished in 5.24s
```

The test detects the mutation **cleanly and without a hang**. The test runs
the shutdown in its own thread and waits with a limit; a blocking shutdown is
reported as an error and the job is then released.

### Assessment

| Aspect | Result |
|---|---|
| Do the tests detect the examined defects? | **Yes**, both. |
| Do they report cleanly instead of hanging? | **No** → fixed (section 5, change A3). |
| Do the tests cover the core promises? | Yes: priority order, fairness, queue limit, cancellation before/during the execution, session lifecycle, panic isolation, worker limit, counter. |
| Open gap | There exists **no** test that checks that the **UI thread** is not blocked. This proof is only possible on a device/emulator and was therefore carried as **NOT RUN** (section 6). |

## 7. Conclusion

The **core claims** of M1.4b/M1.5 are confirmed: real MuPDF engine on Android,
reproducible cross build, ARM64 execution with a real PDF, pixel-exact image
comparison, a common job manager with real job execution.

The **platform and release readiness statements** were too optimistic: the
native library integration would have **prevented the start of the
application** on a real device, the 16 KB compatibility was missing, and the
UI thread was blocked in the PDF viewing path. All four points are now fixed
and secured by an automatic gate.

**The lesson for the acceptance:** the proof "`readelf` shows the correct
`DT_NEEDED` entry" was correct and nevertheless insufficient. Only the
**actually produced APK** made the defect visible. From now on
`scripts/verify-android-native-libs.sh` checks the resolvability, and the APK
check is part of the Android gate.

**The second lesson:** while building the new end-to-end test a **third**
severe defect showed up that none of the previous checks had touched:
`shutdown()` waited **without a limit** for the workers. A job body that
ignores its cancellation token — exactly the case for which the doc comment
wrote "blocks the shutdown, that is a deliberate contract" — thereby also
blocked the **`Drop` of the executor**. The application could **not exit** in
that state. The contract is now implemented: the shutdown is bounded
(`shutdown_grace_ms`), a stuck worker is detached, and a test checks this
property. A defect in the test code made the hang visible — a defect that no
green test run would have shown.
