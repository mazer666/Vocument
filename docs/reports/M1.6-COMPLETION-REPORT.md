### The third severe defect

The new end-to-end test brought out a **third** severe defect that none of the
previous checks had touched: `shutdown()` waited **without a limit** for the
workers. A job body that ignores its cancellation token — exactly the case the
doc comment described as a "deliberate contract" — therefore also blocked the
**`Drop` of the executor**. In that state the application **could not exit**.
The shutdown is now bounded (`shutdown_grace_ms`, default 2 s); a stuck worker
is detached.

The hang was not found by a green test run, but by a **failed** one: the panic
triggered the `Drop`, the shutdown waited, the test process did not terminate.
A test that hangs is a finding, not diligence.

### The release APK is checked

The open item of the first version has been caught up: the release build ran
through with the profile-aware native build (95 MB instead of 196 MB), and the
package was checked with the new gate `verify-android-native-libs.sh --apk` —
all four libraries present, closure resolvable, 16 KB compatible.

### Robustness against difficult files

Eight pathological PDFs (damaged cross-reference, truncated file, page without
an area, 20000 × 20000 points, cyclic page tree, missing content object,
encrypted file, 200 pages) run through the real engine without a crash, without
a hang and with clean errors. The peak memory of the entire corpus is 8.3 MB,
valgrind reports 0 errors and 0 bytes lost. AddressSanitizer remains **NOT
RUN** (nightly toolchain needed).

## F. The licensing decision

The template exists: `docs/decisions/LICENSING-AND-DISTRIBUTION-DECISION.md`.

| Variant | Core |
|---|---|
| **A — AGPL conforming** | The application code must be disclosed; no licence costs; strategically hardly reversible once the code is public |
| **B — Commercial** | No disclosure; **the costs and the minimum turnover are not publicly documented** and have to be asked for; the architecture stays unchanged |
| **C — Alternative engine (PDFium)** | Solves the problem technically through a permissive licence, but with a **loss of function in the PDF mutation** (rotation, annotations) and a high migration effort |

**Recommendation:** variant A, as long as the disclosure is strategically
desired; otherwise variant B. Variant C is the way back if a proprietary
distribution becomes mandatory — the `PdfEngine` trait keeps the way open.

**Open and to be decided by the project owner:** E1 (disclosure?), E2
(proprietary?), E3 (order of magnitude), E4 (server service → AGPL §13), E5
(legal review).

**Until the release is approved:** Do not treat a public distribution as
approved; the producer line and the AGPL note in the PDF metadata are to be
implemented regardless.

## I. Next milestone

On the basis of the **actually reached** quality the following is
responsible:

### 1. Access to a device and a host (a precondition, not code)
A physical Android device **or** an emulator with KVM acceleration, plus a
macOS host. That makes the three open gates executable:
`verify-android-runtime.sh`, the Swift build, the UI measurement.

### 2. The completion of the release readiness on the devices
* On-device run: start the APK, open a PDF, page/zoom/rotation, text, OCR
* UI measurement with defined thresholds (`UI-009`)
* Unpack the release APK and check it (location: `lib/`, no duplicates, 16 KB)

### 3. The licensing decision (E1–E5) — organisational
Before any publication. The template exists; the decision is missing.

### 4. Then: M1.7 — battery and thermal adaptation (`BIGMOBILE-001`)
That is the only technically open remainder of the M1 milestone. It needs
`PlatformAppLifecycle` (foreground/background change) and a real measurement
environment.

### 5. Only afterwards: the Windows and Linux track (`CR-0003`)
The order macOS → Android → Windows → Linux is binding. Windows is **not
yet** responsible as long as macOS is not built and Android is not verified on
a device.

**Not** responsible as the next step: a migration of the engine (variant C) —
it would be a reaction to a licensing decision that has not been made and
would reduce the functional breadth of the product without necessity.
