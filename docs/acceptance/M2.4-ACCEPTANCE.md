## 1. What this slice is about

A reviewer does not write free text on a document. Every note carries a
**meaning**: "this has to be clarified", "I dispute this", "agreed", "a question
to the other party". The colour of the note says what the note means — and
the rail that makes the meaning readable at a glance is the **rail of the
profession**.

Two things therefore belong together:

1. **the comment** — a note that stands on the page, carries its text, its
   author and its time, and can be read back by another tool;
2. **the rail** — the set of colours and their meanings, which the user may
   edit.

The rail lives in the core, not in the interface: the engine gets a colour,
the core decides which colours exist and what they mean. A shell that sends
a colour of its own is refused — the rail is the thing that makes the notes
of a document readable.

## 3. How it is built

The layers stay apart, as everywhere else in Vocument:

| Layer | What it does | Where |
|---|---|---|
| **Engine** | Writes and reads the note: a standard PDF `/Text` annotation with a popup, with the identifier in `/NM`, the author in `/T`, the text in `/Contents` and the time of the change in `/M` | `engines/pdf-mupdf/csrc/mupdf_comment_bridge.c`, `engines/pdf-mupdf/src/comment.rs` |
| **Core** | Owns the rail, checks it, refuses a note that does not fit it, and runs the note as a transaction | `core/vocument-core/src/annotations.rs`, `core/vocument-core/src/transactions.rs`, `core/vocument-core/src/session_mutations.rs` |
| **FFI** | Makes the rail and the notes available, and names the refusal | `platform/vocument-ffi/src/annotation_dto.rs` |
| **Shell** | Shows the rail, lets the user write a note and take it back | `apps/macos/Sources/VocumentMacKit/DocumentCoreClient.swift`, `apps/android/app/src/main/java/org/vocument/app/DocumentCoreBridge.kt` |

The engine carries **no rule of the profession**: it does not know that a
red note means an objection. It writes the colour it is given and reads it
back. The core looks up the colour of the key in the rail and refuses a key
that the rail does not carry.

## 4. The note as a document object

A note is a standard PDF annotation, not a private format:

- `/Subtype /Text` with a `/Popup` next to it, so the text of the note opens
  where the reader expects it;
- `/NM` carries the identifier, so the note can be found and taken back;
- `/T` carries the author, `/M` the time of the change;
- `/C` carries the colour of the rail.

A tool of another vendor reads the note. The interoperability gate with
Acrobat, Foxit and Okular is still open (see section 6).

## 5. What the tests prove

**The engine** (`engines/pdf-mupdf/src/comment_tests.rs`) writes a note into a
document, finds it again, opens the written document a second time and finds
the note there; removes the note and gets its text back; refuses a note
without a text and a note on a page that does not exist.

**The core** (`core/vocument-core/tests/annotation_tests.rs`) proves the
rail: the standard rail carries more than one colour, and every colour has a
name and a meaning; a key that the rail does not carry, a note without a text
and a note without an area are refused; a rail without a colour, a rail with
an entry without a name and a rail with a key that stands twice are refused.

**The chain** (`platform/vocument-ffi/tests/annotation_e2e_tests.rs`) walks
the whole path: a note is written over the FFI boundary and read back with
the colour of the rail; the document is saved and opened again and the note
is there; the note is taken back and brought again; the note is removed; a
note with a key that the rail does not carry is refused **and the bytes of
the document stay the same**; the rail of the user replaces the default and
the colour of the note follows.

**The shell** (`apps/android/app/src/test/java/org/vocument/app/DocumentCoreBridgeTest.kt`)
proves that the rail reaches the caller and that the user may replace it.

## 6. What is not proven in this round

- **The surface of the applications**: the user marks a place on the page,
  chooses a colour of the rail, writes the text and reads the notes again.
  No macOS host and no device are available: the step of the interface is
  **NOT RUN**. The library layer and the bridge are proven.
- **The interoperability with the tools of other vendors** (Acrobat, Foxit,
  Okular): the note is a standard PDF annotation, but the comparison with an
  external viewer is still outstanding — the M2 gate.
- **The behaviour on a device** (Android, macOS): no device, no `/dev/kvm`.
- **The rail of the user in the interface**: the core takes the rail of the
  user, checks it and gives it back; the surface that offers the rail to
  edit it is part of the macOS slice of M2.
- **The appearance of the note**: MuPDF draws a text annotation as an icon
  with a colour. Whether the icon suits the profession is a question of the
  surface, not of the document.
- **The notes in the search**: a note is not part of the text of the page, so
  the full-text search does not find it. Whether the notes shall be searched
  is a question of the surface of the search.
