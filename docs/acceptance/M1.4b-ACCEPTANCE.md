## 2. Gate Criteria & Evidence

### M1.4b Gate: Real PDF engine on Android, verified on ARM64

> *"Replace the Android placeholder bridge with a reproducible, cross-compiled MuPDF build, and prove on the ARM64 target that real PDFs are opened, rendered and mutated — not simulated."*

1. **Binary evidence (`scripts/verify-android-arm64-pdf.sh`, step 2):**
   ```text
   ✓ MuPDF library: libmupdf.so.28.5 (ARM aarch64, SONAME libmupdf.so.28.5)
   ✓ The Android engine links against the real MuPDF (libmupdf.so.28.5)
   ```
   The link probe is compiled against the installed headers and the resulting
   `NEEDED` entry is compared with the SONAME of the installed library. A stub
   cannot satisfy this check.

2. **Execution evidence (step 4), output of the ARM64 harness:**

   ```text
     first line: Vocument Preface and Navigation Overview
     PASS a display list can be created
     PASS a page can be rendered
     page 0 render: 595x842, ink ratio 0.0058
     PASS the rendered page contains visible content
     PASS a display list can be created
     PASS a page can be rendered
     page 1 render: 595x842, ink ratio 0.0085
     PASS the rendered page contains visible content
     PASS a display list can be created
   ```

   The "ink ratio" is the share of non-white pixels in the rendered page. A
   placeholder engine that returns a blank bitmap would report an ink ratio of
   0.0000 and would fail the check.

3. **Image based regression evidence (step 5):**

   ```text

   ```
   (exit code 1)

## 4. Defects found and fixed during this milestone

| Defect | Fix |
|---|---|
| The `mutool` command line tool could not be linked for Android (`unable to find library -lpthread`), which aborted the whole build although only the library is needed. | The build stops after the shared library; the installation is done manually. |
| The MuPDF library path used `${MUPDF_VERSION%%.*}` (`libmupdf.so.1`), while MuPDF produces `libmupdf.so.28.5`. | The version specific file name is used consistently. |
| The `libmupdf.so` produced by the cross build was an x86-64 object, because the host linker was used. | The NDK `LD` is used explicitly, including the `-m aarch64linux` target emulation that the LLVM linker requires for the embedded font resources. |
| The interoperability gate failed on hosts with MuPDF in a custom prefix: `mutool` was not found and, once found, could not load `libmupdf.so`. | `platform/vocument-ffi/src/interop_dto.rs` searches additional prefixes and sets `LD_LIBRARY_PATH` for the reference renderer. |

## 5. Scope limitations and NOT RUN items

| Item | Status | Reason |
|---|---|---|
| On-device verification of the Android app (APK, camera, OCR) | **NOT RUN** | No Android device, emulator or Android SDK/Gradle environment is available in the current environment. The on-device gate is `scripts/verify-android-runtime.sh`; it is binding and cannot be skipped, but it cannot be executed here. |
| Android APK build via Gradle | **NOT RUN** | No Android SDK is available. The native cross build of the Rust core for `aarch64-linux-android` **is** verified. |
| MuPDF's PKCS#7 / digital signature support on Android | **NOT IMPLEMENTED (documented)** | The Android NDK ships no OpenSSL, so the module is disabled with `HAVE_LIBCRYPTO=no`. Vocument does not implement digital signatures yet (`REQUIREMENTS.md` §27). Recorded in `ADR-0017`. |
| Source offer for the AGPL on the Android distribution | **OPEN** | The mechanism (in-app link, source archive, build-time bundle) is not yet decided. Recorded as `RISK-009`; it must be settled before the first public Android release. |
| APK size increase through `libmupdf.so` (roughly 55 MB) | **ACCEPTED** | Recorded as `RISK-010`; reducible later by dropping unused formats and shipping per-ABI splits. |
