## 1. What it is about

A link in a document is rarely only a link. It may open a page, call up an
address on the network, start a program, submit a form — or run a script that
is never shown to the reader.

For a professional review it therefore matters not only *where* a link leads,
but *what* it does. The inspection answers both.

## 3. How it is verified

The evidence runs against a **real PDF** with five links and one document-wide
action:

| Element of the test document | Expected result |
|---|---|
| `/OpenAction` with `/JavaScript` | `JavaScript`, risky, **without** a page |
| Link with `/GoTo` to a destination inside the document | `InternalDestination`, **not** risky, with a position |
| Link with `/URI` to `https://example.com/review` | `Uri`, risky (it leaves the machine) |
| Link with `/JavaScript` | `JavaScript`, risky, with the script text |
| Link with `/Launch` to `calc.exe` | `LaunchFile`, risky, with the file name |
| Link with `/URI` to `file:///etc/passwd` | `Uri`, risky (local file) |

In addition the following is checked:

- **The position in the right space.** The annotation lies in the user space of
  the PDF (origin at the bottom left, y ascending). What is reported is the
  page space (origin at the top left, y descending) — 72 000 … 92 000
  milli-points for an annotation at y 700…720 on a page of height 792 pt. The
  test computes this; a confusion of the two spaces would therefore be caught
  immediately.
- **Emptiness.** A document without actions yields an empty list, not an error.
- **The counting.** The report counts the risky findings (5) and the findings
  that leave the document (2) separately.

## 4. The separation of layers

The inspection is deliberately split into two layers:

- The **engine** reports the facts: type, target, position. It knows the action
  types of the PDF specification.
- The **core** decides the risk. That is a product decision, not a property of
  an engine — and it is testable without a PDF (three core tests without a
  single file).

The platform only presents the finding. It does not follow any link itself.

## 5. What showed up while building it

**MuPDF does not keep link annotations in the annotation list of a page.**
`pdf_sync_annots` skips `/Link` and `/Popup` — they are loaded separately as
clickable areas. The first version of the bridge walked `pdf_first_annot` and
therefore **found nothing**: the inspection reported an empty list for a
document with five links. The test showed that immediately.

The bridge therefore reads the `/Annots` array of the page directly. That has
a second advantage: only this way the **type** of the action can be determined
at all — the loaded link areas carry only the target, not the action type.
Exactly the information that matters ("this is a script, not a link") would
have been lost.

Also noticed: the catalogue is not the trailer, but the `/Root` of the trailer.
The first access read the trailer and did not find the open action.

## 6. What is not proven in this round

- **The interface.** On macOS this function belongs to a view that shows the
  findings before a click. Without a macOS host **NOT RUN**.
- **The actual following of a link.** The core reports, it does not follow.
  The implementation of the call (system browser, confirmation) belongs to the
  interface and has not been started.
- **Interoperability with the tools of other vendors**: the roadmap demands it
  as an M2 gate; it is outstanding for all M2 functions.
