# Milestone Acceptance Record — M2.1: Secure Redaction with Verification

- **Milestone:** `M2.1 — Secure redaction with verification` (first slice of `M2 — macOS Professional Review`, `ROADMAP.md` M2)
- **Status:** **PASS (host)** — the redaction is implemented, verified with the real MuPDF engine and proven across the FFI boundary; the macOS interface remains **NOT RUN** (no macOS host)
- **Requirements:** `REDACT-001`, `REDACT-002`, `REDACT-005` (`REQUIREMENTS.md` §24)
- **Quality gate of the roadmap:** *redaction extraction/search verification*

---

## 1. Why this slice comes first

M2 delivers nine functions for the professional desktop workflow. The macOS
part of it — comments, stamps, comparison, signature inspection, link and
attachment inspection — can only be proven on a macOS host with a macOS
interface. This environment has no macOS host.

The **redaction** is different: it is security-critical, and it can be proven
completely on the host, because the MuPDF engine on the host is the same one
that runs on the device. A mistake here would not be cosmetic — it would leave
confidential content in files that the user believes to be cleaned. That is
why it comes first.

## 2. The core of the problem

A redaction that only draws a black rectangle over the text is not a redaction.
The text stays in the file stream, it stays extractable, it stays findable
through the search.

For a scan there is a second carrier of the same text: the text layer of a
scan is an **invisible** text (`3 Tr`) over the image. A redaction must remove
that text as well — and the **image pixels** under the region must disappear,
otherwise the image keeps carrying the words.

## 4. How it is verified

The core checks four things separately, because they have different failure
modes:

| Check | What it proves | Limit |
|---|---|---|
| **Text layer** | The words of the region are no longer readable through the engine path, and **nothing lies in the region any more** — a fragment of a word counts as content | decisive |
| **Search** | The full-text index (FTS5) no longer contains the words | decisive |
| **Picture of the page** | On the rendered image of the page nothing is readable at the place of the region anymore | decisive |
| **Places in the document** | The engine reports every place of the document that still carries the removed text: the content streams, the annotations, the form values, the embedded files, the metadata and the XMP packet — as plain text, as UTF-16 in both byte orders and as the hex string of the UTF-16 bytes | decisive for the places it looks at; the content of the other pages is not part of the redaction, the user marked a region of this page |
| **File bytes** | The words are no longer present in the file as plain text | supplementary — it looks at the whole document, so a word that legitimately occurs somewhere else refuses the redaction. The check over the places is the one that is precise. |

The check against the picture of the page is the core of it: **the page is
rendered and read with the OCR**, exactly as a reader sees it. Because the
redaction **does not draw a black box** over the region, the image shows the
truth. A box would hide content that survived the removal — the check would
then be worthless, because it would only see the covering.

The set of checked words is **word by word**, not line by line: only the words
whose centre lies in the region have to disappear. A line in which only one
word was redacted keeps its other words.

The removal works **character by character**. A region that covers only a part
of a word therefore leaves a fragment behind — and a fragment is still content.
The verification therefore compares fragments as well: a word that is a prefix
or a suffix of a removed word is a survivor. A fragment of a **single**
character is not compared — a single character such as `|` occurs in every
PDF file and would be no evidence of a leak. The region check covers it
nevertheless: nothing may lie in the redacted region any more.

The words that the checks look for in the whole document need at least four
alphanumeric characters. The region check is independent of that limit and
covers every word, however short it is.

## 5. What the review found and what was fixed

The first version of the redaction was claimed to be secure. It was not.

| # | Finding | Severity | Fix |
|---|---|---|---|
| 1 | **The removed text stayed in the bytes of the file.** MuPDF writes unreachable objects into the file when the garbage collection is not requested. The old content stream object was still in the file: after the redaction the text was no longer extractable, but still readable. | Critical | `opts.do_garbage = 1` when writing; the test checks the bytes, not only the extraction |
| 2 | **The image pixels of the region stayed untouched.** `PDF_REDACT_IMAGE_REMOVE_UNLESS_INVISIBLE` would have removed the whole page image (the page would be lost). `PDF_REDACT_IMAGE_PIXELS` replaces the affected pixels and leaves the rest of the image alone. | Critical | Switch to `PDF_REDACT_IMAGE_PIXELS`; the proof is a marker inside the uncompressed image stream |
| 3 | **The black box covered the content.** It made the picture of the page useless as evidence: surviving content would have been invisible behind it. | High | `black_boxes = 0`. The redaction draws nothing over the region; the picture of the page shows the truth. The interface shows the removed words to the user. |
| 4 | **The verification only checked the words the core had determined itself.** Text that was not part of that set would have stayed undetected. | High | A word-accurate set based on the word boxes of the engine; in addition the page is rendered and read |
| 5 | **A redaction without content was reported as a success.** The user would have believed that something was removed. | High | A region without text and without visible content is refused with `NothingToRemove` |
| 6 | **An unverified result could be treated as a success.** The `verified` field was only a hint. | High | The FFI reports an incompletely verified redaction as an **error** (`RedactionUnverified`). There is no way to treat it as a success. |
| 7 | **The coordinates were documented wrongly.** The boxes of the engine lie in the page space (origin at the top left, y descending). The documentation named the PDF user space (origin at the bottom left). | Medium | Documentation corrected in core, FFI and engine; the conversion in the rendering reader adjusted accordingly |

### 5.1 The second review: an independent adversarial audit

The record above was written by the team that built the feature. A second
review was therefore commissioned: two auditors who had no part in the
implementation tried to **break** the guarantee with their own harness, built
against the production bridge and linked against MuPDF 1.28.5, with `mutool` as
the independent reference.

They broke it. Eleven findings, of which five were critical or high:

| # | Finding | Severity | Fix |
|---|---|---|---|
| 8 | **The word boxes of a turned page were inverted.** The box of a word was built from the upper-left and the lower-right corner of a character. On a page turned by 90 degrees the box came out inverted, the redaction failed with status 7, and on a page turned by 180 degrees only the first and the last character were removed — while the verification reported success. | High | The box of a word is now the bounding box of all four corners of all of its characters; the distance between two characters is measured along the reading direction of the line. Proof: `the_word_boxes_of_a_turned_page_are_normalised`, `a_redaction_removes_the_word_on_a_turned_page` |
| 9 | **A redaction that covered only a part of a word left a fragment behind.** The removal works character by character; the verification compared whole words, so a readable fragment of the secret was reported as a success. | Critical | The verification compares fragments (a word that is a prefix or a suffix of a removed word is a survivor) and it checks the redacted region itself. Proof: `a_redaction_that_only_covers_a_part_of_a_word_is_not_reported_as_successful` |
| 10 | **The text of an annotation, the value of a form field, the metadata and the XMP packet survived the redaction** — and the check over the bytes only saw plain text, so a text stored as UTF-16 or as the hex string of the UTF-16 bytes was not found at all. | High | The engine cleans those places and reports every place of the document that still carries the word, in all of these encodings. A place that cannot be cleaned (an embedded file) makes the redaction fail. Proof: `the_text_of_an_annotation_and_of_a_form_field_is_emptied`, `a_word_that_is_hex_encoded_is_found` |
| 11 | **There was no rollback.** The removal happened before the verification, the checkpoints of the recovery store were deleted, and the caller received an error that said nothing about the state of the document. The user could hold a changed document and believe that nothing had happened. | High | A redaction that cannot be verified is rolled back: the bytes are restored, the search index is built again, the transaction of the attempt is removed and the checkpoints are only deleted after a successful verification. Proof: `a_redaction_that_cannot_be_verified_leaves_the_document_unchanged`, `a_redaction_that_cannot_be_verified_leaves_the_document_and_the_checkpoints_alone` |
| 12 | **Words with fewer than four characters were not checked** and not named in the report. | Medium | The region check covers every word, however short it is; the limit of four characters remains only for the checks that look for a word in the whole document |
| 13 | **The text of a Type 3 font is not removed by MuPDF at all** (`recurse = 0` in `init_redact_filter`). The auditors measured 8322 dark pixels before and after the redaction. | Critical | Such a document is now reported as **not verified**: the region check sees the text that survived. The redaction is refused instead of reported as a success |

The findings and their measurements are in
`docs/audit/redaction-security-audit.md` and
`docs/audit/redaction-pdf-qa-audit.md`.

### 5.2 The third review: a second adversarial audit

A second independent audit went further than the first one. It built a
document in which the same word stands on two pages, it split a word over
several objects, it hid a secret in the alternative text of an annotation
and in the XMP packet of a page, and it measured the whole chain from the
call to the app. It found **nine gaps on the document level** and **fifteen
along the chain**; the reports are in `docs/audit/`.

What it found, and what was changed:

| # | What was wrong | What was changed |
|---|---|---|
| 1 | A word that is only partly covered left a readable fragment behind ("GEHEIM" → "HEIM"), and the report did not mention it: the word was not in the list of the removed words, because its centre lay outside the region | A word that the region **touches** belongs to the redaction, and the region grows to the whole word. The words of the picture count as well |
| 2 | The XMP packet **of a page** was neither cleaned nor reported — it is a compressed stream, so neither the byte check nor the text layer saw it | The scrub and the search for the places cover the packet of every page |
| 3 | A word that is spread over several objects was not recognised | The region takes every word it touches, so both parts of a word in the marked region go. A word whose parts lie **apart** from each other remains a limit (section 7) |
| 4 | A three-letter secret in `/Alt` survived, and the search and the byte check reported "passed" **without having checked anything** | The exact checks carry **every** word, however short it is; a check that could not be carried out is `NotChecked`, never a pass. The annotations are cleaned down to their alternative text |
| 5 | A place of the document that the engine could not clean stopped the redaction and was **not named** | The places are named in the error |
| 6 | After a failed verification the revision of the session stayed on the higher value: the document was marked as changed although nobody touched it | The revision goes back with the bytes |
| 7 | The picture check was a difference check: a word that the OCR could not read before was never in the list | The check looks at the picture itself: nothing may be readable at the place of the removed word any more. The limit of the OCR remains (section 7) |
| 8 | The same word on another page was not mentioned in the report | The report names the places where the same word still stands |
| 9 | A secret in Base64 stays undetected | Not fixed — a limit of the search (section 7) |
| 10 | Errors **after** the mutation left the document changed and reported an error that said nothing about it | Every error after the removal puts the document back |
| 11 | The chain ended in the generated code: no application called the redaction | The macOS client and the Android bridge call it and check the report themselves |
| 12 | The crash recovery applied a redaction **without verification** | The recovery does not replay a redaction and says so |
| 13 | The checkpoints of the recovery store were readable for everybody (0644) and hold the document in plain text | They belong to the user alone (`0600`) |
| 14 | A failure while deleting the checkpoints turned a **successful** redaction into an error | The failure of the recovery store does not undo the redaction |

### 5.3 The fourth review: a third adversarial audit

A third independent audit attacked the redaction that the two audits before it had hardened.
Two checkers worked in parallel: one on the document itself, one on the chain from the call to
the application. The document checker built 30 purpose-made PDF files — a popup that does not
stand in `/Annots`, a structure tree, a name tree, optional content, private data, an attached
archive, a word that occurs twice on the same page — and measured the redaction against
`mutool` and against the raw bytes of the file. The chain checker measured the exported UniFFI
ABI with a C program and compared the generated bindings with the checked-in ones. The reports
are in `docs/audit/redteam-round-three-document-level.md` and
`docs/audit/redteam-round-three-platform-chain.md`.

What it found on the document level, and what was changed:

| # | What was wrong | What was changed |
|---|---|---|
| 1 | **The search and the cleaning worked with a list of known places.** A popup that does not stand in `/Annots`, the structure tree, the optional content, the name tree and the private data of a page carried the secret — and the redaction reported success | Both walk through **every** object of the document now (`mupdf_walk.h`). Every string and every stream is offered with the place it lies in; the cleaning empties the strings, the search reports what is left |
| 2 | The check over the bytes was switched off as soon as the word occurred legitimately somewhere else — a secret in a place that the search did not visit was not noticed | The cause is gone: the search visits every place now. The byte check remains the supplement it always was |
| 3 | The checks looked at the **whole document** instead of the marked place: a word that occurs twice on the same page refused every redaction of that word | The checks of the text layer and of the search index are scoped to the marked place. A word that stands elsewhere on the page is reported, not refused |
| 4 | After a rolled back redaction the session kept the revision of the attempt and claimed unsaved changes | The session is synchronised with the transaction manager in the rollback |
| 5 | A word that only stands **next to** the region was removed with it | The rule "the region takes every word it touches" now requires a **real overlap**; two boxes that only share their edge do not overlap |
| 6 | A word of three letters is not looked for in the bytes of the file | Unchanged and documented — the other three checks are exact and carry every word, however short it is |
| 7 | The content of an attached archive cannot be read: the secret can stay in the archive | The redaction names such a place (`uninspected_places`) and does not claim that the text is gone from there |

| 3 | The revision after the recovery was the one of the journal, not the one of the state that was applied | The redactions that were not replayed are subtracted from the revision |
| 4 | Old checkpoints kept the mode `0644` | Every checkpoint is made private when the next one is written |

### 5.4 The fifth review: the fourth adversarial audit

The fourth audit did not attack the redaction from the outside any more. It
attacked the **rules that the third round had introduced**: the walk through
the document, the container recognition and the sweep over the
cross-reference table. It built 20 purpose-made PDF files and measured the
redaction against the real chain from the core to MuPDF to the UniFFI
boundary.

The finding that mattered was **critical**:

> The walk handed the objects of the cross-reference table on as **direct**
> objects. `pdf_is_stream()` works on the *number* of the object — a direct
> object has the number zero, and the answer is therefore always "no". The
> content of a form XObject was therefore never looked at. A secret in the
> content of a form object stayed in the document, and the redaction reported
> `verified = true`.

The rest of the findings:

| # | What was wrong | What was changed |
|---|---|---|
| 1 | The walk did not descend into the **dictionary of a stream** — a form object carries the resources and the text of the user in its dictionary | The walk descends now. The copy is found as a **hidden** place, the redaction **refuses** and names the place, and the document stays byte for byte unchanged (criterion 39) |
| 2 | The **identifier of the file** in the trailer (`/ID`) was never seen — it is not an object of the cross-reference table | The trailer is walked now; the identifier is cleaned like every other place |
| 3 | A container was only recognised under the name `/EmbeddedFiles` — the same archive was refused there and accepted under `/AF`, and the redaction reported success while the secret stayed in the archive | The decision is made from the **content** of the stream, not from the name of the path |
| 4 | The words of the **`/Encrypt`** dictionary were cleared — they are the keys of the document, and clearing them destroys the encryption of the file | The encryption dictionary is never walked and never cleared. It is named in the code and in the comment that says why |
| 5 | The sweep over the cross-reference table was **quadratic** — the list of the seen objects was a linear list | The seen objects live in a table with open addressing now; the sweep is linear |
| 6 | The recovery directory was checked for its mode, but **not for its owner** — and the FFI swallowed the error with a message on the console | The owner is checked now, the store **refuses every write** into a directory that does not belong to the user, and the reason reaches the user as a **status** (`document_core_recovery_status()`) |
| 7 | The sweep reached the objects that the writer had already removed | A free entry of the table is skipped, and an object that cannot be read is skipped instead of being guessed |

The report of the checker lies in the repository:
[the fourth audit on the document level](../audit/redteam-round-four-document-level.md),
with its raw protocol
([774 lines](../audit/redteam-round-four-measurements.txt)). The harness, the twenty attack
files and the redacted output documents stay in the working directory of the release team —
they are the tools of the attacker, not a part of the product.
The part that the round changed is not only a bug: it is a **rule**. A
redaction of a document that carries a form object with text in it does not
succeed any more. That is the correct behaviour, and it is proved by the
end-to-end test of criterion 39.
### 5.5 The sixth review: the fifth adversarial audit

The fifth audit attacked the **whole chain** — the core, the engine and the
exported UniFFI functions — with 32 purpose-made PDF files, and checked every
output with two independent oracles: a scanner of the auditor's own (plain
bytes, Flate, raw Deflate, LZW, UTF-16 in both byte orders, hex-encoded
UTF-16) and the text extractor of `mutool` 1.28.5. The encryption of the
attack files was validated byte for byte against a file that MuPDF itself
wrote.

**No critical finding.** In every one of the 26 attacks in which a secret
survived, the redaction **refused** and named the place — and the document
stayed byte for byte unchanged. The critical finding of the fourth audit (the
walk did not see the content of a stream) is closed and stays closed.

Three findings:

| # | What was wrong | What was changed |
|---|---|---|
| **R5-1** (medium) | The clearing emptied the **`/U`** of an encrypted document when the encryption dictionary is an **indirect** object — the form the specification asks for (ISO 32000-1, Table 15). The protection of the key `/Encrypt` of the trailer did not apply to that path, because the sweep over the cross-reference table reaches the dictionary by its **number**. The proof: `the_keys_of_the_security_dictionary_are_not_emptied`, `the_security_dictionary_is_not_a_place_that_carries_the_text`, `a_document_with_an_indirect_encryption_dictionary_stays_encrypted`. ## 6. Undo and recovery

A redaction **cannot be undone**. The removed content is gone; an undo that
brought it back would be a lie. The transaction manager therefore refuses the
undo explicitly instead of failing silently.

In addition, the **checkpoints of the recovery** are deleted with the
redaction: they hold the bytes of earlier states of the document, and the
removed text would still be in them. They are deleted **after** the
verification has succeeded — before that, the removal can still fail.

A redaction that cannot be verified is **rolled back**: the bytes of the
document are put back, the search index is built again, and the transaction of
the attempt is removed from the transaction manager, so that the journal of
the recovery store cannot replay a redaction that never happened. The caller
receives an error, and the document is the document it was before.

Likewise the transaction command carries **no text**: it is written into the
persistent journal, and the journal must not contain the content that was just
removed.

## 7. What is not proven in this round

- **The macOS interface** (comment bar, redaction tool, keyboard workflow): no
  macOS host available. The redaction is available across the FFI boundary,
  but **no application calls it yet**: the tool of the interface is part of the
  macOS slice of M2, which cannot be built or run here.
- **The Android interface** of the redaction: no device available, and the
  same applies — the function is available across the FFI boundary, the
  application does not call it yet.
- **The behaviour on a device** (Android, macOS): no device, no `/dev/kvm`.
- **Interoperability with the tools of other vendors** (Acrobat, Foxit,
  Okular): the roadmap demands it as an M2 gate. On the host `mutool` is
  available; a comparison of the redacted file with an external viewer is
  still outstanding.
- **Comparison corpus, signature and attachment inspection**: M2 functions that
  have not been started. The signature and the attachment inspection exist as
  of M2.3 (`SIGREV-001`, `ATTACH-001`).
- **The interoperability of the redaction with the tools of other vendors**
  (Acrobat, Foxit, Okular) and the **behaviour of a redacted document in a
  viewer that does not know the redaction**: still outstanding.
- **The same word somewhere else in the document.** The redaction removes
  what the user marked — a region of one page. A word that occurs on
  another page, or a second time on the same page, is **not** part of the
  redaction: the report names those places (`remaining_occurrences`), so the
  shell can show them, but the redaction itself is not refused — otherwise
  no document with a word that occurs twice could be redacted at all. The
  promise of the redaction is about the marked region; the promise that a
  secret is nowhere in the document is the job of the full sanitising
  (`SAN-001`), which has not been started. A remainder in the bytes of the
  file **without** a known place — an old version of the file, an unreachable
  object — still stops the redaction.
- **A document that carries the text in a Type 3 font**: the first audit
  assumed that MuPDF 1.28.5 cannot remove such a text (`recurse = 0` in
  `init_redact_filter`). The second audit **could not reproduce** that: the
  text of a Type 3 font was removed completely in the construction it built.
  The claim is therefore withdrawn for that construction; the other
  constructions — glyph procedures with their own CTM, a Type 3 font in an
  XObject — were not checked exhaustively. Should such a construction
  survive, the check over the region sees it and the redaction is refused
  (the document is left unchanged) — but the text is not removed.
- **A secret that is encoded in Base64** stays undetected: the search looks
  for plain text, for UTF-16 in both byte orders and for the hex string of
  the UTF-16 bytes. A Base64 encoded secret would need the decoded forms of
  every word.
- **A word whose parts lie apart from each other**: the region takes every
  word it touches, but a word that the author wrote in two pieces that lie
  far apart is not one word in the text layer. The remain of the second
  piece is therefore not a fragment of the first one. Such a document needs
  the full sanitising (`SAN-001`).
- **The proof of the picture rests on the OCR**: text that the OCR cannot
  read at all cannot be proven to be gone by the OCR. For a scan without a
  text layer this is the only proof besides the picture itself. An OCR that
  reads **nothing** is not distinguishable from a page that is clean: the
  report does not carry the number of words the OCR read.
- **The content of an attached archive**: a ZIP archive (or a RAR, or a 7z
  file) holds its content compressed. The redaction cannot look into it, and
  it does not delete an attachment — the data of the user belongs to the
  user. Such a place is named in the report as a place that could **not** be
  read (`uninspected_places`), and the callers turn it into a warning. The
  redaction does not claim that the text is gone from there.
- **The clipboard of the user** keeps the text that was removed until the
  redaction surface clears it. No application calls the redaction yet, so
  there is no place where the clearing could happen.
- **The recovery store lies in the temporary directory** by default
  (`RecoveryStore::default_app_store`). Its content belongs to the user alone
  (`0700`/`0600`), but a directory in the temporary directory is predictable and
  can be prepared by somebody else. The applications have to hand the store a
  directory of their own — the sandbox of the application.
- **The performance of the sweep over the cross-reference table** was not
  measured with a document of 32 000 objects. The sweep is linear by
  construction (the table of the seen objects has open addressing), but a
  **measurement** of the time is **NOT RUN**. A document of that size is also
  the only way to see whether the redaction of a large file stays in the
  time that a user tolerates.
- **The interoperability of the redaction with the form objects** of the
  documents of other producers: a document with a form that carries text in
  its content is now **refused** by the redaction. That is the safe answer,
  but it means that such a document cannot be redacted at all until the
  sanitising (`SAN-001`) can empty the content of a form object.
