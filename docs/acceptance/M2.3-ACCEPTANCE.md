## 1. What it is about

Two questions that a document can answer about itself, and that come first in
a professional review:

1. **Which files are hidden in this document?** An attachment can be a program
   that starts when it is opened. An attachment can also not be in the document
   at all, but only name a path — then the document points outside.
2. **Does the document carry a signature, and does it still cover its
   content?** A document can be signed and modified afterwards. The signature
   is still there — but it says nothing about the content any more. Exactly
   that has to be visible to the reviewer.

## 3. How it is verified

The evidence runs against a **real PDF** with an embedded attachment and a
signed form field. The test document is built in two variants:

| Variant | Byte range of the signature | Expected result |
|---|---|---|
| unchanged | covers the **entire** file | `changed_since_signing = false`, not risky |
| modified | covers only the **beginning** of the file | `changed_since_signing = true`, risky |

The byte range is written with a fixed number of digits (the same file is
built twice, the second time with the real values), so that the offsets stay
valid. There is therefore no test document whose signature is valid only on
paper.

Checked in addition:

- **The attachment.** `anhang.exe`, type `application/octet-stream`, content
  inside the document, checksum matches (none is stored) → reported as risky
  because the name names a program.
- **The signature.** Field `Unterschrift`, signature `Dr. Weber`, time
  `2026-01-31T12:00:00Z`, reason `Freigabe`, place `Berlin`.
- **Emptiness.** A document without attachments and without signatures yields
  empty lists, not an error.

## 4. The separation of layers

As with the action inspection, the **engine** reports the facts and the
**core** decides the risk.

One exception is deliberate: **whether the document was modified after the
signature is decided by the engine.** Only it can read the byte range of the
signature and compare it with the size of the file. The core then only
decides what that means — a document that was modified after the signature
carries a signature that no longer covers anything.

## 5. What showed up while building it

**The MIME type of an embedded attachment has to be masked in the PDF name.**
`/Subtype /application/octet-stream` is syntactically **wrong**: the slash is
a delimiter in a PDF name, so the name ends after `application` and the rest
is read as a new key. MuPDF then reports `invalid key in dict` and the object
stays unreadable — without an error in the document. The correct form is
`/Subtype /application#2Foctet-stream`.

**The change check needs the field, not the signature.** MuPDF's
`pdf_signature_incremental_change_since_signing` checks itself whether the
passed object is a signature field and throws otherwise. The byte range is
read through the value of the field. The first version passed the value — the
error `annotation is not a signature widget` gave it away.

**The checksum is an optional piece of information.** Without `/CheckSum`
there is nothing to check; MuPDF reports this as valid. The report states
both: whether a checksum is stored and whether it matches.

## 6. What is not proven in this round

- **The caller.** The macOS client and the Android bridge call the
  inspection and hand the report over. The **step of the interface** is the
  macOS slice of M2.
- **The interface** on macOS: the list of attachments with a confirmation
  dialog, the signature overview with the notice "modified after the
  signature".
- **The verification of the signature itself** (chain, validity,
  certificate): MuPDF offers no public interface for it in this version. What
  is checked is the *coverage* of the signature — the document as it is, not
  the mathematical validity of the signature. That is a deliberate limit, not
  a claim.
- **The behaviour on a device** (Android, macOS): no device, no `/dev/kvm`.
- **Interoperability with the tools of other vendors**: outstanding as an M2
  gate for all M2 functions.
